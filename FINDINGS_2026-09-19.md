# Re-judging the opponent features against the metric that matters

**2026-09-19. Reproduce with `python exp_reevaluate.py`.**

Two changes were sitting unshipped. Opponent difficulty had been built,
measured and **rejected** (`opponent.py`). The goalkeeper fix had been
diagnosed and deliberately left alone (`FINDINGS_2026-09-11.md`).

Both were re-run together, as a 2×2, because both change what the model
learns from and two changes measured separately can each look neutral and
still interact.

---

## Why re-open a settled rejection

Opponent difficulty was rejected on the **ranking** metric: mean actual points
of the top-20 picks per gameweek, 4.39 → 4.27. The same experiment recorded
high-return MAE **improving**, 5.305 → 5.169, and treated that as a
consolation prize.

Then GW4 was scored live on 2026-09-15, the first graded gameweek this project
has ever produced:

| model | MAE | high-return MAE |
|---|---|---|
| `two_stage_ml` | **1.126** | 5.353 |
| `form_fdr` | 1.213 | **4.572** |
| `naive_form` | 1.277 | 4.601 |

The champion wins on the average and loses badly on high returns — the half
that decides a gameweek. **That is precisely the thing opponent difficulty
improved.** The feature may have been rejected on the wrong metric.

---

## THE MISTAKE I MADE FIRST, AND THE DOCUMENT THAT CAUGHT IT

The first run of `exp_reevaluate.py` let the goalkeeper fix change the **test**
set as well as the training set, and reported:

```
champion       MAE 0.954      keeper fix   MAE 0.912
```

Those are the exact numbers `FINDINGS_2026-09-11.md` already calls superseded,
for the exact reason it gives:

> goalkeeper rows have MAE ~0.58, far below outfield, so adding them drags the
> mean down regardless of skill

26,320 test rows against 29,747. It measures **composition** and reports it as
**skill**. The paired bootstrap was worse still: with different-length arrays
it was pairing unrelated players by position in the list.

Corrected design: **keepers are always in the frame and always in the test
set, for every arm; only the training set changes.** That is also what
production genuinely does — it predicts 71 keepers a week from a model that
has never seen one.

The champion's real MAE on that common test set is **0.905**, not 0.954. Every
number below is on identical test rows.

---

## Results

Trained on 2022-23 → 2024-25, tested on 2025-26, held out entirely.

| arm | MAE | high-return MAE | ranking pts/pick | train rows |
|---|---|---|---|---|
| champion | **0.905** | 5.266 | **4.39** | 74,440 |
| + keeper fix | 0.912 | 5.206 | 4.29 | 83,513 |
| + opponent | 0.916 | 5.098 | 4.29 | 74,440 |
| **+ both** | 0.923 | **5.052** | 4.31 | 83,513 |

Paired bootstrap over gameweeks, 2000 draws:

| arm | ranking | high-return MAE |
|---|---|---|
| + keeper fix | −0.107, CI [−0.262, +0.042], P(better) 0.07 | **−0.061, CI [−0.071, −0.050], P(better) 1.00** |
| + opponent | −0.100, CI [−0.283, +0.086], P(better) 0.14 | **−0.168, CI [−0.182, −0.155], P(better) 1.00** |
| + both | −0.081, CI [−0.226, +0.062], P(better) 0.14 | **−0.214, CI [−0.228, −0.200], P(better) 1.00** |

---

## What this says

**The trade is real, consistent, and in one direction.**

Every arm improves high-return MAE, every one with a confidence interval that
excludes zero and P(better) = 1.00. The combination is best: **−0.214**, a 4%
reduction in error on exactly the players the live scoreboard says the model
handles worst.

Every arm costs a little on ranking. None of those losses is statistically
clear — all three intervals cross zero — but they lean consistently negative,
and for the keeper fix 93% of bootstrap samples showed it worse. It is weak
evidence of a real cost rather than no evidence.

Overall MAE gets slightly worse across the board, which is expected: the model
is being pushed to spend capacity on the tail rather than the average.

**So this is a genuine trade-off, not a free win.** Better on the metric that
decides gameweeks, probably slightly worse on the metric the project has been
optimising, and that is a judgement about what the engine is for.

---

## Recommendation: do not promote. Run it as a challenger.

Promoting mid-season would also silently corrupt the accuracy scoreboard, since
GW4 was graded against the current champion and a replacement would be scored
under the same name.

The scoreboard already compares three models side by side. Register `+ both`
as a fourth, log its predictions alongside the champion's each week, and let
real gameweeks decide. That is the roadmap's own "champion/challenger
promotion" item, done with live evidence rather than a backtest.

**Two backtest gameweeks of disagreement is not enough to overturn a metric
the whole project was built on. Six live ones would be.**

### Order of operations, because one of these is unsafe on its own

1. Register the challenger and log both models per gameweek. Safe: additive,
   changes no existing prediction.
2. Score both live for several gameweeks.
3. Promote only if the live high-return gap holds and ranking does not
   collapse.

The goalkeeper fix must **not** be applied to the champion on its own before
step 1. `recommend.py` uses `INSERT OR REPLACE`, so retraining rewrites
predictions already logged for the current gameweek and destroys the ability
to grade it.
